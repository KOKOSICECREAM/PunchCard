# Contract audit — 2026-09-13

First compilation of the suite as a set. Every finding below was produced by the compiler
or by `forge build --sizes`, not by reading. Reproduce with the settings in
[`building.md`](building.md).

> **Update 2026-09-13:** all six defects are fixed. Every contract now compiles and fits
> under EIP-170. The suite has never been deployed or tested against live Uniswap
> contracts, so treat it as ready for a testnet deployment, not a mainnet one.

**Bottom line (at time of audit): the suite could not be deployed.** Two blockers are architectural, four
were structural and are mechanical to fix. None of this is visible from reading the code,
which is why it survived: `artifacts/` only ever contained `WindDownController`, so the
suite had never been built.

---

## Blockers

### 1. TokenFactory exceeds the EIP-170 contract size limit — ✅ FIXED

| | Bytes |
|---|---|
| `TokenFactory` runtime size | **35,149** |
| EIP-170 limit | 24,576 |
| **Over by** | **10,573** |

The deployment transaction will fail on Base mainnet. Every other contract has comfortable
margin — `LPLocker` 9,171, `PunchCardRouter` 9,595, `RewardEscrow` 3,884.

**Cause.** `deploy()` uses `new MerchantToken(...)`, `new VestingWallet(...)` and so on,
which embeds the full creation bytecode of all five suite contracts inside the factory.

**Options.**
- **EIP-1167 minimal proxy clones** — deploy each suite contract once as an implementation,
  then `clone()` per merchant and call an `initialize()`. Cuts the factory dramatically and
  makes per-merchant deploys much cheaper. Cost: the suite contracts must move their
  constructor logic into initializers, and `immutable` variables cannot be used in a clone
  (they would become regular storage). That weakens a real guarantee — several contracts
  rely on `immutable` addresses.
- **Split the factory** — a `SuiteDeployer` helper the factory calls, or a two-transaction
  deploy. Keeps `immutable` intact. Less elegant, preserves the security properties.

> The `immutable` question decides this. The docs and marketing lean on "immutable after
> deploy"; naive cloning would turn those into ordinary storage variables. **Recommend
> splitting the factory rather than cloning**, unless someone deliberately re-argues the
> trust model.

**Fixed by splitting.** Construction moved into two permissionless helpers,
`SuiteDeployer` (token, vesting, treasury, escrow) and `LockerDeployer` (LP locker). Two
rather than one because the five contracts together are 27,772 bytes of initcode, over the
limit for any single holder. The factory reaches them through interfaces only — importing
the concrete deployers would pull the bytecode straight back in.

| | Before | After |
|---|---|---|
| `TokenFactory` runtime | 35,149 | **10,974** |
| Margin | −10,573 | **+13,602** |

Every `immutable` in the suite is preserved, so the trust model is unchanged.

### 2. The Uniswap pool is never created or price-initialised — ✅ FIXED

`deploy()` calls `INonfungiblePositionManager.mint()` for both pools but never calls
`createAndInitializePoolIfNecessary`. There is no `sqrtPriceX96` anywhere in the codebase.

The merchant token is created in Step 1 of the same transaction, so its pools cannot
already exist. `mint()` reverts against an uninitialised pool.

**`deploy()` therefore reverts 100% of the time, for every merchant, even once the size
problem is solved.**

There is a second half to this. `sqrtPriceX96` is what *sets the launch price*. Right now
nothing does, so "the ratio of pair amount to fixed token count sets the price" is not
actually implemented. Both pools must be initialised to the same implied price, or the
first trade is free money:

```
USDC pool: usdcPairAmount / 1,800,000 tokens
ETH  pool: ethPairAmount  / 1,200,000 tokens   (× ETH/USD at deploy time)
```

**Fixed.** `deploy()` now calls `createAndInitializePoolIfNecessary` for both pools with a
`sqrtPriceX96` computed by `LaunchPricing.encodeSqrtPriceX96()` from the amounts each pool
is about to receive.

The price-mismatch half is fixed structurally rather than by convention: the launch token
split is no longer the fixed 1.8M/1.2M but is derived from the USD value seeded into each
pool, so both open at the same price for any seed. Seed amounts became minimums ($2,000
USDC / $3,000 ETH) with no upper bound. Covered by `test/LaunchPricing.t.sol`, including a
fuzz test that the split always sums to `LAUNCH_LP_ALLOC` exactly.

## Structural defects — mechanical to fix

### 3. Interfaces declared inside contract bodies — ✅ FIXED
`TokenFactory`, `LPLocker`, `PunchCardRouter` each declare interfaces *inside* the contract.
Solidity does not permit this: *"Function, variable, struct or modifier declaration
expected."* They must be at file level.

### 4. `RewardEscrow.refill()` declares `mainPool` twice — ✅ FIXED
Lines 151 and 167, same scope — *"Identifier already declared."* The second is the
post-refill balance used for the low-pool warning. Rename it.

### 5. `INonfungiblePositionManager` declared twice, with different members — ✅ FIXED
`TokenFactory` declares one with `MintParams`/`mint`; `LPLocker` declares another with
`positions`/`increaseLiquidity`. The illegal nesting in #3 is the only reason they don't
already collide — fixing #3 surfaces the clash. Extract one shared interface into
`contracts/interfaces/`.

### 6. Requires `via_ir` — this is a deployment fact, not a preference — ✅ FIXED
Without the IR pipeline `TokenFactory.deploy()` fails with "Stack too deep". Recorded in
`foundry.toml`. **The same settings must be used for Basescan verification.**

## Reviewed and sound

Worth saying explicitly — the core design holds up.

- **`MerchantToken`** is genuinely clean: no owner, no mint, no pause, no clawback, fixed
  supply. The "your token is immutable" claim is true.
- **Allocation arithmetic is exact.** 15M + 10M + 45M leaves precisely `LP_ALLOC` (30M),
  asserted in-contract; 3M seeds the pools leaving exactly `LP_RESERVE` (27M).
- **Uniformity is enforced by the code, not by policy.** Every allocation, cap, cliff and
  delay is a `constant` in the factory. A merchant cannot negotiate different terms —
  which is the whole premise of the network.
- **`distributeReward` follows checks-effects-interactions**, decrementing `dailyBalance`
  before transferring, and is `nonReentrant`.
- **Validation in `deploy()` is thorough** — zero-address checks on all three wallets,
  fee-tier whitelisting, `perTxFloor`/`perTxMax` bounded by `DAILY_CAP`, and
  `msg.value == ethPairAmount`.

## Found later — router (2026-09-13)

### The price-impact guard compared different assets — ✅ FIXED

`swap()` required `amountOutMinimumHop1 >= amountIn * 0.95`. Those are denominated in
different tokens: merchant tokens are 6dp at ~$0.002, USDC 6dp at $1, WETH **18dp**. As a
raw integer comparison it **blocked token→token, token→USDC and WETH→token outright**,
while being a trivially-satisfied no-op on token→WETH and USDC→token.

The cross-merchant swap — the feature the network thesis rests on — could never execute.

Removed rather than repaired. `amountOutMinimum` is already passed to Uniswap and is
correct slippage protection computed by the caller from a quote. A genuine impact check
needs a price reference, and a TWAP of a $5k launch pool is too cheap to push to trust.

### The minimum was enforced pre-fee but paid post-fee — ✅ FIXED

In `_swapTokenToStable`, Uniswap checked `amountOutMinimum` against the gross output, then
the router skimmed its fee and paid the remainder. A caller could receive up to `feeRate`
less than the minimum they specified, contradicting the struct's own comment. Now checked
against the amount actually delivered.

`_swapStableToToken` was already correct — it takes the fee from `amountIn` before swapping,
so the minimum applies to what the recipient receives.

## Found by testing the wind-down (2026-09-13)

### LPLocker.release() double-counted collected fees and bricked wind-down — ✅ FIXED

`release()` accumulated merchant-token amounts returned by `collect()` into
`totalMerchantBurned`, then added `balanceOf(address(this))` to the same total. But
`collect()` pays into this contract, so those amounts were **already inside the balance**.
The burn therefore asked for `collected x 2 + reserve` against a balance of
`collected + reserve` and reverted with "burn amount exceeds balance".

It triggered whenever a position had earned any merchant-token fees — i.e. always, in
practice. And `onExpiryReleaseLP` is the **terminal step** of the wind-down, so the failure
was permanent: the merchant's LP could never be released, and the suite would sit in a
half-settled state forever with no path out.

Fixed by burning the balance rather than a running total. Covered by
`test_lpReleaseSplitsAndBurns` and `test_windDownCompletesOnAnEmptySuite`.

## External review (Codex, 2026-09-13) — all four fixed

An independent review found two real defects and two hygiene issues. Both defects are
worth recording because neither was caught by this repo's own tests.

### 1. DeployMerchant approved USDC from the wrong wallet — ✅ FIXED

`TokenFactory.deploy()` pulls USDC from `p.ownerWallet`, not from `msg.sender`. The script
approved from the broadcaster. In production the broadcaster is PunchCard's deployer hot
wallet — `deploy()` is `onlyDeployer` — and `ownerWallet` is the merchant, so the approval
did nothing and every real onboarding would have reverted on `transferFrom`.

**The fork test passed only because it set `MERCHANT_OWNER` to the broadcaster.** The test
configuration hid the bug, which is the more useful lesson: a passing integration test
proves the path it was configured for, not the path production uses.

Now requires the merchant's allowance to already exist, with an error that says so.

**Follow-up from the same review:** the first fix compared `msg.sender == owner` to decide
whether to auto-approve. That is unreliable — `msg.sender` in a forge script before
`vm.startBroadcast()` is the script's sender, which depends on `--sender`, `--account` and
the forge version, not necessarily the broadcast signer. Identity inference is gone; a
`MERCHANT_SELF_APPROVE` flag declares the intent explicitly for local and testnet runs, and
getting it wrong reverts immediately on `transferFrom` rather than mis-approving silently.
The runbook now documents the exact two-transaction choreography.

### 2. addLiquidity could strand reserve tokens permanently — ✅ FIXED

`require(usdcTokenAmount > 0 || ethTokenAmount > 0)` only checked the token halves, but
each mint branch runs `if (tokenAmount > 0 && pairAmount > 0)`. So
`addLiquidity(1_000_000, 0, 0, 0)` added no liquidity at all, yet still ran
`_reserveTokens -= (usdcTokenAmount + ethTokenAmount)`.

Those tokens stayed in the locker's balance but were no longer counted as reserve: they
could never be deployed as liquidity again, and were burned at wind-down. A merchant
fat-fingering one call would silently lose that slice of their 27M. Each side now requires
both halves or neither. Covered by `test_addLiquidityRejectsHalfASide`.

### 3. Liquidity adds had no slippage protection — ✅ FIXED

`addLiquidity` hardcoded `amount0Min`/`amount1Min` to zero, so a merchant deploying reserve
could be sandwiched — the pool price moves between submission and inclusion and the mint
accepts whatever ratio it lands on. The function now takes four `*Min` bounds. The factory's
launch mint still passes zero, which is defensible there because pool creation and mint are
atomic in the same transaction.

### 4. ERC-20 return values were unchecked — ✅ FIXED

`SafeERC20` adopted across `RewardEscrow`, `TreasuryTimelock`, `VestingWallet`,
`PunchCardRouter`, `LPLocker` and `TokenFactory`. Base USDC and WETH behave, so this was
hygiene rather than a live bug, but it removes a class of weird-token behaviour and every
auditor would have flagged it.

## Second external review (Codex) — reserve drain

### LPLocker.addLiquidity let a merchant drain the entire LP reserve — ✅ FIXED

**Severity: critical.** The 27M LP reserve is meant to be locked, released only into
liquidity at the merchant's own pace. It could be taken outright.

Dust from `increaseLiquidity()` was returned to `ownerWallet` regardless of which token it
was, and `_reserveTokens` was decremented by the **desired** amount rather than the amount
Uniswap actually consumed. Uniswap bounds liquidity by whichever side is scarcer, so:

```
addLiquidity(27_000_000e6, 0, 1, 0, 0, 0, 0, 0)   // 27M tokens against 1 unit of USDC
```

consumes almost no merchant tokens, and the remainder is transferred straight to the
merchant as "dust" while the reserve is decremented by the full amount. One call, and the
accounting still looks consistent afterwards. The `*Min` bounds do not help — the merchant
sets those and would pass zero.

Now: pair-token dust is returned (it is the merchant's own capital), merchant-token dust
stays in the locker and stays counted as reserve, and `_reserveTokens` decrements by actual
usage. Approvals to the position manager are also zeroed after each add.

The same pattern existed in `TokenFactory`'s launch mint, where merchant-token dust also
went to `ownerWallet`. Low-risk there because the pool is created at exactly the price
implied by the seed amounts, so dust is rounding-level — but it is the same hole. Fixed by
returning only pair-token dust; merchant-token dust now falls through to the step-9 sweep
that moves the factory's remaining balance into the locker as reserve.

> **Botched on the first attempt, caught on the next review.** The script meant to fix both
> pools asserted its way to a crash on the second branch *before* writing the file, so the
> successful first replacement was discarded with it. A follow-up patched only the ETH
> branch and the USDC branch was left vulnerable — with the ETH comment pointing at a note
> that did not exist. The lesson is not about dust: **when a scripted edit fails partway,
> re-verify the whole target, not just the part you retried.**

The mock originally did not pull consumed tokens out of the caller, which let a weaker
balance invariant pass than production permits. It now transfers them, and the test asserts
the strong invariant — `balanceOf(locker) == reserveTokens()`, every merchant token held is
accounted reserve — before and after the add.

`test_addLiquidityCannotDrainReserveAsDust` encodes the exploit. Verified meaningful by
reinstating the old behaviour: the test fails with 9,990,000 tokens drained from a
10,000,000 offer, and passes once fixed.

Also from this review: `RewardEscrow` now asserts `perDay * MAX_DRAWER_DAYS <=
type(uint128).max` at construction, so the drawer bookkeeping bound is proved rather than
reasoned about.

## Verified, not just reviewed

**The slippage-bound mapping.** `addLiquidity` maps four `*Min` values onto Uniswap's
`amount0Min`/`amount1Min` by token ordering, in two places. A reversed mapping does not
revert — it silently protects the wrong asset, so a merchant believes they are covered and
is not. That function was edited three times with nothing checking it.

The mock now records what the locker actually asked Uniswap for.
`test_slippageBoundsMapToTheCorrectSideOfEachPair` asserts both orderings in one call: the
merchant token is token0 in the USDC pool and token1 in the ETH pool, so the mapping has to
flip between them. Distinct sentinel values make any swap unambiguous.

Verified meaningful by reversing each pool's mapping in turn — the test fails on both
(`2222 != 1111` for USDC, `3333 != 4444` for ETH) and passes only when both are correct.

## Open questions, not yet defects

- **LP trading fees were stranded** — `LPLocker` had no way to collect them outside
  wind-down, so they accrued untouchably in the position. Fixed by `collectFees()`.
- ~~**LP dust is returned to `ownerWallet`**~~ — **resolved.** The merchant-token half was
  not a question but a critical bug: it made the LP reserve drainable, and the same pattern
  existed on both factory launch pools. Merchant-token dust now stays locked everywhere.
  Pair-token dust is still returned, which is correct — it is the merchant's own capital.
- **`refill()` is permissionless.** Intentional, as far as I can tell, and harmless since
  it only moves tokens between the escrow's own buckets.
- **WETH dust** is asserted to zero for USDC and the merchant token, but not for WETH.
